# CPU 侧性能优化建议（AI 分层 / 动画 LOD / 内存分配）

> 前提说明：本文件的所有**实测数字**取自 Apple M1 / Chrome 157 / 1440×810 / 系统负载 < 4。
> 标注「预期」的条目是**基于测量的推算，尚未实现验证**。
> 若目标设备不是 M 系列/独显（如集显笔记本、移动端），结论的优先级需要重排——见第 5 节。

---

## 0. 现状基线（实测）

| 指标 | 数值 | 来源 |
|---|---|---|
| JS 脚本耗时（128 人） | **5.89 ms/帧** | CDP `Performance.getMetrics` → `ScriptDuration` |
| ├ 游戏逻辑（不含渲染） | 1.99 ms | 单独计时 `__dbg.step` |
| └ 渲染提交（含 composer） | 3.88 ms | `composer.render()` + `gl.finish()` |
| 任务耗时（main thread） | 6.68 ms/帧 | CDP `TaskDuration` |
| 分配速率 | **≈1.6 KB/帧**（实测 1478–1795 B/帧） | CDP `HeapProfiler.startSampling` |

> **更正**：本文早期版本写「19.4 KB/帧」，那是用 `performance.memory` 堆增量估的，被量化误差放大约一个数量级。
> 可靠方法是 CDP 堆采样（`HeapProfiler.startSampling` + `samplingInterval: 1024`），实测约 **1.5–1.8 KB/帧**。
> 因此「内存分配优化」的实际权重远低于最初判断。
| 堆占用 | 27–30 MB（长跑稳定） | `performance.memory` |
| draw call | ~200（128 人） | `renderer.info.render.calls` |
| 帧预算占用 | 6.7 / 16.7 ms = **40%** | 计算 |

**关键判断**：当前利用率 40%，GPU 与 CPU 都未饱和。因此这些优化的目标**不是提高上限**，而是：

1. 在**低配/繁忙机器**上把峰值压回 60 fps（今天 load 6 时掉到 44 fps 就是峰值问题）
2. 为将来 100+ 单位同屏留出余量

如果只面向 M 系列 + 独显，**这些优化当前都不必要**，应优先投玩法（见第 5 节）。

## 1. AI 分层（收益最高）

### 适用的瓶颈
JS 脚本耗时中「每单位每帧的固定开销」。当前 `updateEnemies` 对**全部**存活单位每帧执行：状态机推进、追击/攻击判定、分离求解、碰撞推出、朝向插值。距离 50 m 外的单位对玩法零贡献，成本却与近处相同。

### 具体措施

| 编号 | 措施 | 说明 |
|---|---|---|
| **A1** | **按距离分档更新** | ≤18 m → 60 Hz（现状）；18–35 m → 20 Hz；35–60 m → 10 Hz；>60 m → 5 Hz。用累加器实现，与动画 LOD 同相位，避免两套相位 |
| **A2** | **远场群体代理** | >35 m 的单位**不参与** `separateUnits` 与 `resolveBlockers`，位置直接按速度积分（队形整体漂移），不查 grid/blocker |
| **A3** | **令牌按距离加权** | `attackTokens` 已限流；再让远处单位更难拿到令牌，避免远处"看不见的攻击"消耗近战名额 |
| **A4** | **角度判定降频** | 仅 <35 m 做精确 `angDiff` 判定；远处用缓存朝向，跟随判定降为 10 Hz |

### 对玩法体验的影响

- **<18 m：完全不变**——玩家所有交互都发生在这个范围，这是"不能动"的部分
- **18–35 m：20 Hz 更新**。位置仍由速度积分，视觉移动连续；风险在**状态切换**（chase→wind）会有 50 ms 抖动。缓解：状态切换点做一次朝向/位置对齐
- **>35 m：群体代理**。远处只见整体移动，看不到个体动作；玩家接近到 35 m 时切回完整 AI。**切换瞬间的位置跳变**是最大风险，缓解办法是切回时用 0.3 s 插值把代理位置与真实位置对齐
- **A3 的影响是手感**：远处单位不再"抢攻"，近处压力更集中——这通常让战斗更清晰，但需要实测确认不会让近处过难

### 验证指标

| 指标 | 怎么测 | 期望 |
|---|---|---|
| `scriptMs`（需新增 `__dbg.info().scriptMs`） | CDP 或页内累加 | 128 人时 5.89 → **≤4.2 ms** |
| 帧时间 p95（不只是均值） | 采 300 帧，取 95 分位 | 繁忙机器上 p95 ≤ 25 ms |
| 近战行为不变 | 现有 18 条 + 新增「分层开关 A/B 下，近处单位 10 s 内攻击次数一致」 | 差异 ≤ 5% |
| 无视觉跳变 | 录 20 m 外单位走近的连续帧，检查位置连续性 | 单帧位移 ≤ 0.35 m |
| 玩法断言 | 分层开/关各跑一次 60 人站桩 | 掉血量与击破数差异 ≤ 5% |

### 成本与风险
成本：中（累加器 + 距离分档 + 切换对齐）。风险：中（跳变、状态抖动）。

## 2. 动画 LOD（已有基础，可再压一层）

### 适用的瓶颈
`AnimationMixer.update` 与骨骼矩阵写入。当前已按 60 / 20 / 10 / 0 Hz 分档（18 / 35 / 60 m），这部分**已经做完了**。

剩余问题：**>60 m（0 Hz 档）的单位仍每帧写一次 `mesh.position/rotation`**（因为要跟随移动），并且仍在场景图里参与矩阵更新。

### 具体措施

| 编号 | 措施 | 说明 |
|---|---|---|
| **B1** | **远场实例化代理** | >60 m 的单位改用 `InstancedMesh` 代理（复用已有 shadow proxy 的思路），骨骼完全冻结，只更新实例矩阵 |
| **B2** | **混合降精度** | 远场动画只做 2 帧线性插值（现有 `previous/target` 已具备），不再走 `crossFadeTo` |
| **B3** | **固定步长驱动** | `mixer.update` 改用固定步长累加，避免不同 LOD 档之间相位漂移导致的"抖动" |

### 对玩法体验的影响
- 远处单位动作僵硬/静止——**60 m 外看不清，无感知**
- 靠近时切回完整动画（18 m 档），切换点做一次 `mixer.setTime` 对齐
- **无玩法影响**（纯视觉 LOD）

### 验证指标
- `renderer.info.memory.textures` 稳定不涨（B1 会减少 skinned mesh 数）
- `skinnedMeshes` 数：128 人时从 128 → 期望 **≤40**（近场才建骨骼）
- 帧时间 p95
- 视觉：60 m 边界处来回走动，检查无突现/跳变

### 成本与风险
成本：中高（要维护"代理 mesh ↔ 骨骼 mesh"两套表示）。风险：中（切换瑕疵）。

## 3. 内存分配（19.4 KB/帧，收益被低估）

### 适用的瓶颈
GC 停顿。1.2 MB/s 的分配速率下，128 人时约每 2–4 s 触发一次 minor GC。在**空闲机器**上无感（60 fps 有 10 ms 余量吸收），但在**繁忙机器**上 GC 会与其它进程叠加，表现为周期性掉帧——这正是今天 load 6 时 44 fps 的一部分原因。

堆本身稳定（27–30 MB），所以**不是泄漏，是分配频率**。

### 具体措施（按预期收益排序）

| 编号 | 措施 | 位置 | 预期 |
|---|---|---|---|
| **C1** | **HUD 文本值变才写** | `updateHUD` 里 `UI.ko.textContent = player.ko` 等每帧赋值会创建字符串 | 省 2–4 KB/帧 |
| **C2** | **伤害飘字去字符串** | `popDamage` 的 `'暴击'/'弹反'/'破防'` 字面量每次拼接 | 省 1–2 KB/帧 |
| **C3** | **粒子对象池核查** | `burst()` 若每次新建数组/对象 → 改池（需先用分配采样确认） | 视情况 |
| **C4** | **热路径去 `new`** | 搜索每帧每单位执行的 `new THREE.Vector3()` / `new THREE.Color()` / 数组字面量 → 复用模块级临时对象 | 省 1–3 KB/帧 |
| **C5** | **DOM 写入节流** | 连击数/计时器每帧写 `textContent`（计时器每秒才变） | 省 1 KB/帧 |

**注意**：C1/C2/C5 是"零风险、纯收益"，应当**先做**；C3/C4 需要先做分配采样定位热点，不要盲改。

### 定位方法（重要）
不要用 `performance.memory`（它是量化更新的，逐帧不可靠，我实测拿到全 0）。
正确做法：
1. CDP `HeapProfiler.startSampling({samplingInterval: 4096})` → 跑 4 s → `stopSampling`
2. 按 `callFrame.functionName + url:line` 聚合样本数，得到分配热点排序
3. 或 Chrome 任务管理器 → "JS 堆大小" 观察增长斜率

### 验证指标
- **分配速率**：同样方法测 KB/帧，目标 **19.4 → ≤8 KB/帧**
- **p95 帧时间**：繁忙机器上应更平稳（GC 尖峰减少）
- **14 轮 soak**：堆曲线仍稳定在 22–46 MB（不能因为池化引入泄漏）
- 玩法断言不变

### 成本与风险
成本：低（C1/C2/C5 各 5–20 行）。风险：低。

| 占比 | 函数 | 归属 |
|---|---|---|
| 13.3% | `setValueV3f` (three:18400) | three 内部（uniform 上传） |
| 11.2% | `setValueM4` (three:18525) | three 内部 |
| 10.2% | `separateUnits` (index:2778) | **本项目** |
| 9.2% | `multiplyMatrices` (three:6224) | three 内部 |
| 8.2% | `cloneUniforms` (three:12163) | three 内部 |
| 5.1% | `setProgram` (three:30131) | three 内部 |
| 4.1% | `updateEnemyRigs` (index:2206) | **本项目** |
| 4.1% | `updateEnemies` (index:2533) | **本项目** |

**本项目只占约 18%，其余 60%+ 是 three 内部的 uniform/矩阵上传**——这部分靠改业务代码动不了。
`separateUnits` 是本项目最大的单点（10.2%），但它是位置式分离，难以去分配（可改成"输出写入目标数组"而非新建对象）。

## 4. 排序：按「预期收益 ÷ 实施成本」

| 排名 | 项 | 预期收益 | 成本 | 风险 | 建议 |
|---|---|---|---|---|---|
| **1** | **C1 + C2 + C5** HUD/飘字/文本去分配 | 低（实测改动前后 1478 → 1795 B/帧，在噪声内）| **低** | 无 | 已做，收益≈0，但消除每帧 `innerHTML` 解析是净收益 |
| **2** | **A1** AI 距离分档 | **高**（远场 AI 省 60–80%） | 中 | 中 | **建议做** |
| **3** | **C4** 热路径去 `new` | 中（先采样再改） | 低 | 无 | **做（先采样）** |
| **4** | **A2** 远场群体代理 | 高（>35 m 省分离+碰撞） | 中 | 中 | 与 A1 一起做 |
| **5** | **A3** 令牌距离加权 | 低（手感更清晰） | 低 | 手感变化需实测 | 可选 |
| **6** | **B1** 远场实例化代理 | 中（减少骨骼数） | 中高 | 中 | 有余力再做 |
| **7** | **B2** 混合降精度 | 低 | 低 | 无 | 顺手做 |

**先做第 1 项**（半天内可完成、零风险），再评估第 2 项（AI 分层是最大的一块，但需要玩法 A/B 验证）。

## 5. 前提与结论适用条件

| 目标设备 | 结论是否需要调整 |
|---|---|
| **M 系列 / 独显**（当前测试环境） | 利用率仅 40%，**以上优化都不紧急**；应优先投玩法与内容 |
| **集显笔记本（Intel Iris / UHD）** | 渲染先吃紧 → 优先做**分辨率/阴影/后处理降级**（已有 `?low=1`），AI 分层收益次之 |
| **移动端** | 内存带宽与 CPU 都紧 → AI 分层 + 分配优化收益最大；但单文件 700 KB 的解析时间也要考虑 |
| **低配验收线（≥45 fps）** | 当前负载 6 时 44 fps 说明峰值余量不足 → **A1 + C1 是最直接的解** |

**一句话**：这套优化的价值不在于"让 60 变成 90"，而在于**让繁忙机器上的 44 回到 58**。如果目标机器一直是空闲的，收益接近于零。
